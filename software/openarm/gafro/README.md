# The arms on gafro — config

The arm layer that runs the OpenArm through [gafro_robot_interface](https://github.com/personalrobotics/gafro-robot-interface) and
its own CAN driver, with no ROS. The design, the layering and what is and is not verified are in
[`notes/design/arm-gafro.md`](../../../notes/design/arm-gafro.md). This folder is the **config** of that layer:

| File | What |
|---|---|
| `hardware.example.yaml` | the RI hardware config: one `openarm` driver per control group. A **template** — the robot's own copy lives on the robot and is never overwritten by a deploy |
| `../../../description/openarm/gafro/openarm_bimanual.xml` | **the arm's model for this robot**: `openarm_assets`' model with joint 2 capped for the head. Generated by `tools/arm_gafro_model.py` (`--check` says if it is stale) |
| `controllers.yaml` | the controllers, in gafro's control spec: what each does and what it is driven with |
| `../../../tools/arm_ready_pose.py` | the ready pose: `verify` checks its singularity, joint margins and clearance; `pick` repeats the search (ssik + self-motion-charts) |
| `engage.py` | what the moves share: `build` (a controller from the spec), `PathCheck` (the collision check of a straight joint-space line), `PermitKeeper`, `stow_pose`. The torque sequence that was here is removed; `arm_service.py ctl activate\|park` is the way to ready and back to stow |
| `arm_service.py` | the arm service, taking over what `ros2_control` did one slice at a time: holds one arm, publishes `/joint_states` through gafro-ri-ros2-bridge, and takes `ctl activate\|park\|hold\|down\|status` over a unix socket in place of `openarm-up`, gated as `engage.py` is, and serves `/<side>_controller/follow_joint_trajectory` (`ros_actions.py` over `trajectory.py`) for the show runner, `/<side>_gripper_controller/gripper_cmd` (`gripper.py`; tests in `../tests/test_arm_service.py`). The slice list is in its docstring |
| `guards.py` | what the first runs check before they command an arm on a real bus: no other controller on it, CH5 and the e-stop, `--supervised`, and a start near stow or ready. See *What the first runs refuse* in the design note |
| `check.py` | builds every controller for both arms against that model, checks it carries the head cap (and nothing else changed), and that the hardware config adds no second one |

```sh
PY=<venv>/bin/python
PYTHONPATH=<openarm_assets>/src $PY software/openarm/gafro/check.py
PYTHONPATH=<openarm_assets>/src $PY tools/arm_gafro_model.py --check
```

It needs the published gafro and `openarm_assets`. It builds the controllers and does not run them; it touches no arm and no simulator.
CI (`.github/workflows/arms-gafro.yml`) runs only the second command, which needs mujoco and `openarm_assets` and not gafro (a C++ build);
`check.py` is run by hand when the model, the controllers or the gafro they build against change.

## Activate and park

```sh
$PY software/openarm/gafro/arm_service.py ctl --side right activate     # -> the model's `ready` keyframe
$PY software/openarm/gafro/arm_service.py ctl --side right park         # -> the stow file's pose
```

Both are a minimum-jerk straight line in joint space, played in position mode (arm_service.py `_move`, over trajectory.py). The line is checked against the collision geometry first
(`engage.PathCheck`) and refused if a pair of parts comes nearer along it than at its closer end and within 2 cm. The torque controllers that used to do this (`engage`, `track`) are
removed: torque control does not move this arm.

**On a real bus the move is gated** (guards.py), before anything is enabled: the existing stack must not be running and no other sender may be commanding the motors; CH5 must be
MANUAL or AUTO with the e-stop clear (read from the dashboard, `GET /api/choreo/robot`); `--supervised` says a person is at the e-stop **and that head tracking is OFF with the neck centred** (the head moves on its own and is not in the collision model; the plan and the prompt say so); **CH6, the deadman, must be HELD** while an arm moves (the arms are not on the deadman in normal operation, `docs/interfaces/command-telemetry.md`; here it is a hold to run): `lapse` and `move` ask for it once you have typed the joint and direction back, before the first permit is granted, and `engage` and `--park` ask for it at launch; the permit is renewed only while CH5 is MANUAL or AUTO, the e-stop is clear and CH6 is held, so turning CH5 off, pressing the e-stop or letting go of CH6 cuts a running sequence short; and the arm must start within 5 degrees per
joint of stow or ready, because the collision check has no head in its model. A `fake` bus and the simulator are not gated. **Ready is a working pose, not a resting one**: an
e-stop or a power drop there lets the forearm fall, so park before leaving the robot.

`park` reads `/etc/opendubs/openarm-stow.conf` (`OPENARM_STOW_CONF`), the file `openarm-up park` reads: `LEFT_STOW=` and `RIGHT_STOW=`, seven
joint angles in degrees. Unset is refused, not guessed. The angles are taken as the model's, which they are where a robot's driver direction
and zero are the identity; otherwise convert them first.

It asks no permit of anything and is not the authority layer: the arm service calls it once an arm may move. Simulation only so far.

## First run on an arm

`bringup.py` is the first-run checks of one arm, a stage per subcommand, each ending in PASS or FAIL: `hold` (stage 3: verified, enabled and held
with no permit, so it must not move), `lapse` (stage 4: a slow move on a permit, the permit stops being renewed, the arm must stop where it is),
`move` (stage 5: one joint a small step and back). The arm supported, a person at the e-stop, one arm at a time:

```sh
PY=<venv>/bin/python; M=description/openarm/gafro/openarm_bimanual.xml; HW=/etc/opendubs/<the robot's copy of hardware.example.yaml>
$PY software/openarm/gafro/bringup.py hold  --side right --model $M --hardware-config $HW
$PY software/openarm/gafro/bringup.py lapse --side right --model $M --hardware-config $HW --supervised --joint 3 --delta +0.05 --speed 0.03 --after 0.3
$PY software/openarm/gafro/bringup.py move  --side right --model $M --hardware-config $HW --supervised --joint 3 --delta +0.01
```

**A step has no default size or direction.** `--delta` is required and signed (`+0.01`, `-0.01`), at most 5 deg unless `--allow-large`, and the
right sign depends on what the arm stands next to. Before anything is enabled `bringup.py` refuses a step it cannot take, and a `lapse` that cannot pass.
Then, with the arm held at its real pose and before it moves, it (1) checks the clearance along the straight path in the Choreography lane's twin
(`sim/clearance.py`, read and never edited; only pairs involving the arm being moved count) and refuses under `--min-clearance-mm` (20): a floor
and not a margin, since the twin was 6 deg optimistic on the one pose measured on the robot, (2) prints the plan with the pose the arm is at, and
(3) starts only when the joint and direction are typed back (`3+`, or `--confirm 3+` from a script that has read the plan). The twin needs
`--assets` (the openarm_assets checkout, `$ARM_ASSETS` in `env.sh`) and a `sim/` whose twin builds (`--sim-dir`, or `$OPENDUBS_SIM_DIR`); one that cannot be
built is a refusal, not a pass, and `--skip-clearance` goes without it and says so in the plan. The twin keeps its meshes in `/tmp/opendubs_sim_meshes_<hash>`
as links into the checkout that built them: remove that directory when that checkout is removed, or the next build fails on dangling links.

**Why the lapse defaults are `--speed 0.03 --after 0.3`.** The permit stays valid 0.5 s after the last renewal, so the arm keeps following the move for about
`after + 0.5` s. A move shorter than that has finished by then and the stage reports FAIL however well the arm holds: the earlier defaults (0.05 rad at 0.1 rad/s,
after 1.0 s) could not pass, and neither could `--after 0.3` at 0.1 rad/s. At 0.03 rad/s the 0.05 rad move takes 1.67 s and is cut after about 1.3 deg.

With `require_permit: true` the arm holds unless the permit is renewed; `bringup.py` renews it itself (`PermitKeeper`) while they
run and revoke it on exit, and the arm service will do that once it exists. In the simulator (`--backend mujoco`) `hold` and `move` fail by the
sim's own sag, 0.057 rad: its hold is MuJoCo's position servo, which gets none of the driver's gravity feedforward. On the arm that figure is the
thing to look at. Not yet run on an arm.

## The gripper

The driver commands each arm's gripper (one more Damiao motor on the arm's bus, ids 0x08 and 0x18) as RI's `<name>/gripper`, closure 0 open and
1 shut (`set_gripper`, `open_gripper`, `close_gripper`). It needs a calibration that is per robot and has no default,
`gripper_open_position` and `gripper_closed_position`, the motor's angles at fully open and fully shut: **find them with the gripper moving
freely, one robot at a time**, then write them in the robot's copy of `hardware.example.yaml` (commented there) and set `use_gripper: true`.
The speed and torque limits are starting values, and the grasp margin (how far short of closed counts as holding something) is too.

**It cannot be run in the simulator on this model yet.** RI's MuJoCo backend treats an actuator that is not a joint transmission (a tendon
over the fingers) as a gripper, and the OpenArm model has two independent finger-joint actuators, so `get_gripper_names()` is empty there.
The model needs a coupled finger tendon with one actuator for that: a change in `openarm_assets`, not done.

## What lives where

The test for where a setting goes is whose fact it is.

| What | Whose | Where |
|---|---|---|
| Joint ranges, torque and velocity limits, position and velocity gains | the arm's | the model, `openarm_assets` |
| Motor-level protections: torque, velocity, position and slew clamps, trips, hold on a stale command, permit | any OpenArm's | the driver, `openarm-driver` |
| The head cap on joint 2 | this robot's | **the model**, `description/openarm/gafro/`, from `tools/arm_gafro_model.py` |
| CAN names, per-robot direction and zero | this robot's | `hardware.example.yaml` |
| Controller stages, gains, speeds | the task's | `controllers.yaml` |
| CH5, `[AUTH]`, leases, presence, the keeper, the tablet | this robot's | the arm service (not built) |

## Not done

- **The arm service**, which grants the driver's permit and runs the authority layer.
- **A workspace box and the head in the collision model.** gafro's control spec has no position box; the choreography's rule that J2
  stays under 135 deg while the elbow is extended (the 1.2 m box) is not enforced here. The 157 deg cap in `hardware.example.yaml`
  is the backstop for the head contact only.
- **`limits: {joint_torque: model}` does not bind yet.** gafro reads a joint's torque limit from the model, and until the change that
  derives it from the actuators (ga-robotics-research/gafro-research#51) is published, the OpenArm's joints report none. The
  controllers build and run; the bound is not applied.
- **A closed-loop run near the cap has not been done.** (`check.py` used to compare the torque `track` controller's joint 2 torque with and without the cap; with the torque controllers gone, that check is gone, and `follow_pose`'s joint-limit guard is not checked against the cap.)
- **Every number here is a starting value** that has not been run on an arm.

## Testing `arm_service.py`

`tests/test_arm_service.py` (permit, gripper, resampling; no robot) and `tests/test_arm_service_sim.py` (the real process, a trajectory and a pose follow on both arms, in MuJoCo; no ROS) run anywhere
with gafro. Nothing here has run against ROS. On the Thor, `source /opt/gafro/setup.bash`, the old stack down, `--hardware-config /etc/opendubs/openarm-gafro-right-only.yaml`, a person at the
e-stop. Stop at the first rung that misbehaves; the unit file waits for rungs 3 to 6.
